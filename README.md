# Gigspot

Gigspot is a free-first marketplace for client hiring requests and freelancer services. A single account can do both. Contact happens through private chat.

## Local Development

```powershell
npm install
npm run dev
```

Production build:

```powershell
npm run build
```

The public Vite app uses the existing root `.env` Firebase variables. Keep that file private and do not replace its project values. Firebase client configuration is read from `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_STORAGE_BUCKET`, `VITE_FIREBASE_MESSAGING_SENDER_ID`, and `VITE_FIREBASE_APP_ID`.

## Current Listing Policy

- Hiring requests are free and published immediately. Requests may be suspended for policy violations.
- Freelancer services are free and begin as `pending_review`; only an authorized admin can publish or reject them.
- Editing an approved service sends it back to `pending_review`.
- Email verification is required to create listings and start conversations. It is not identity or professional-credential verification.
- Portfolio URLs must be HTTPS, are limited to five, and are not proof of ownership.
- No rating, review, earnings, order-completion, or professional-verification claims are generated by the public UI.

The existing collections remain `jobs`, `skills`, `users`, and `chats`. Existing documents and payment records are not migrated automatically. Legacy pending-payment jobs remain private; legacy phone fields remain stored until a separately approved migration.

## Firebase

`firebase.json` points Functions at `src/functions`, Firestore rules at `firestore.rules`, indexes at `firestore.indexes.json`, and public Hosting at `dist` with a single-page-app rewrite. Deployments are intentionally not run by this repository setup.

The Firebase Functions source still contains legacy Razorpay order/payment handlers. The public UI no longer calls checkout. Do not configure or deploy those legacy handlers as an active product flow without a separate review. Firebase Functions deployment may require the Blaze billing plan; no billing change was made.

Firestore rules enforce verified-email listing writes, listing ownership, service review states, participant-only chats, sender identity, and private payment documents. Rules have not been tested with the Firebase emulator here. Existing documents with public phone fields need an approved migration to remove that historical exposure.

## Internal Admin Console

Run the separate internal app locally:

```powershell
npm run admin:dev
```

It binds to `127.0.0.1:5181`. Build separately with `npm run admin:build`. `dist-admin` is not part of the public app or Firebase Hosting config. Do not publish it without an authenticated access gateway/IAM policy and an approved internal domain. Admin requests require a server-assigned Firebase custom claim; there is no public role-granting endpoint.

See [admin/README.md](admin/README.md) for internal access prerequisites.

## Known External Setup / Limitations

- Enable Email/Password and Google providers and configure authorized domains in Firebase Authentication.
- Add service account admin claims only through an authorized trusted Admin SDK process. The local utility is `node scripts/setAdmin.cjs <firebase-auth-uid> --confirm` and requires the ignored root `serviceAccountKey.json`; do not run it without authorization.
- Functions and the `updateChatSummary` trigger must be deployed before chat summaries stay current; this repository does not deploy cloud resources.
- Firebase Storage is not initialized. Profile-photo uploads need Storage configuration, billing review, and Storage rules; current profile images use existing provider photos or initials.
- No automated Firebase security emulator suite is configured yet.
- Search filters only the pages currently loaded from Firestore (20 per collection at a time); load more to expand the client-side search scope.
- New bookmarks are stored privately under each user's `savedListings` subcollection. Existing public `savedBy` arrays remain unchanged. Before any migration, an authorized operator can run the count-only, read-only audit with `node scripts/auditLegacyListings.cjs --read-only`; it scans in pages and prints counts only. No migration or writes are provided. Any migration needs a reviewed dry run and explicit approval.
- Legacy payment records and Razorpay endpoints are preserved and not treated as active free-first product functionality.
